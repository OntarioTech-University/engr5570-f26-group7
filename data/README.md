# Study subjects (A2, Part 1) · Cris

34 AI-written Python programs from the ASE replication package, each with its
CodeContests tests split into public and hidden tests. Every original program
passes **all** its tests, and every program has something to clean up.

## Files

| File | What it is | Who uses it |
| --- | --- | --- |
| `programs.csv` | One row per program, exactly the Part 1 format | Yujie, Fangyu, Camilo |
| `programs/pNNN.py` | Original program, reads stdin, prints stdout | Fangyu (refactor), Camilo (score) |

| `subjects_meta.csv` | Extra facts per program: problem name, platform, difficulty, prompt condition, test counts, size and complexity, why it was chosen, path of the original file in the ASE package | Everyone, for the A2 tables |

`programs.csv` keeps the six agreed columns only. Anything extra is in
`subjects_meta.csv`, so nobody's code breaks.

## Where the data comes from

* **Programs**: replication package of Zhu, Tsantalis and Rigby, *Understanding the
  Code and Architectural Smells Generated by LLMs and Autonomous Agents* (ASE 2026),
  Zenodo DOI 10.5281/zenodo.19245562, file `replication_package.zip`
  (MD5 `c33a26b249f9bafcc7bdd2cc2cf2f77f`). We use `experiment1/result/`.
* **Tests**: CodeContests (Li et al., AlphaCode), Hugging Face `deepmind/code_contests`,
  revision `802411c3010cb00d1b05bad57ca77365a3c699d6`, the same revision the ASE
  scripts download. All our problems are in train shards 0 to 2.
* **Smells**: the PyExamine reports shipped in the ASE package
  (`code_quality_report.csv`). We copy them as they are into the `smells` column.

## How each program is matched

The ASE result JSON files (`*_output.json`) store the full problem text next to
every program. We look that exact text up in CodeContests to get the problem and
its tests. This is safer than matching by position, because **the ASE models did
not all solve the same problems** (see "Dataset numbers").

Each JSON program is then matched to its `solution_N.py` snippet by comparing the
code with whitespace removed, which gives us the PyExamine smells of that file.

## Public and hidden tests

* `public` = CodeContests `public_tests` (the examples in the problem statement).
  These may be shown to the model in the loop.
* `private` + `generated` = hidden tests, never shown to the model.
* One hidden test of p025 was an exact copy of a public test. We removed it,
  so the hidden suite never repeats a public test.

Totals over the 34 programs: 70 public, 701 private, 2,333 generated tests.

## Selection funnel

Pool: the 5 models analysed in the paper x 2 prompt conditions x 90 problems.

| Step | Removed | Left |
| --- | ---: | ---: |
| Programs in the pool (qwen3-coder-30b zero-shot has no JSON, so it cannot be matched) | | 810 |
| Empty answer (all from Gemini 2.5 Pro few-shot) | 58 | 752 |
| Not Python, mostly C++ or Java answers | 101 | 651 |
| Problem has no public or no hidden tests | 29 | 622 |
| Does not read standard input | 15 | 607 |
| Same code as another program of the same model and problem | 1 | 606 |
| Fails at least one test (353 wrong answer, 52 crash, 17 timeout) | 422 | 184 |
| Slowest test above 1 s (we keep a 5x margin under the 5 s timeout) | 1 | 183 |
| No sign of anything to clean up (rule below) | 135 | 48 |
| Keep one program per problem and model (pick one prompt condition, seeded) | 13 | 35 |
| At most 2 programs per problem | 1 | **34** |

"Something to clean up" means at least one of these, fixed before any refactoring:

1. A PyExamine smell from the ASE data, except Orphan Module and High Fan-in
   (they describe the whole folder, not one program) and Feature Envy and Potential
   Shotgun Surgery (the ASE paper reports them as false positives here).
2. A block with cyclomatic complexity of 11 or more (above McCabe's limit of 10,
   radon rank C). Module-level code counts as one block, because many contest
   programs have no functions and radon would otherwise score them 0.
3. Control statements nested 4 levels deep or more.
4. A function, or the module-level script, with 20 or more lines of code
   (comments, blank lines and docstrings do not count).

Why the 34 programs qualified (a program can have several reasons): long block 24,
deep nesting 20, high complexity 15, ASE smell 9.

## Dataset numbers (checked against the paper)

* The paper analyses **5 models**: Gemini 2.5 Pro, Llama 3.3 70B, DeepSeek-Coder-V2 16B,
  Qwen3-Coder 30B, Qwen3-Coder 480B. The package also has `gemini25f` (Gemini 2.5 Flash)
  and `glm45` (GLM-4.5, few-shot only), which the paper does not report. We leave them out.
* `raw` = Zero-Shot (paper Condition A), `np` = Few-Shot (Condition B). Check: Qwen3-Coder
  480B has 11 Long Method smells in `raw` and 13 in `np`, the same as the paper's Tables 1 and 2.
* Each model and condition has **90 programs** (30 easy, 30 middle, 30 hard), but there
  are **two different problem sets**: Gemini, Llama and Qwen 480B share one set of 90;
  DeepSeek and Qwen 30B (the models run locally with Ollama) share another set of 90.
  Only 41 problems are in both, so the package covers **139 distinct problems**.
* 810 programs in total for the 5 paper models (9 model-condition folders with JSON x 90).
  `qwen_coder_30b/raw` has 97 snippet files but no JSON, so they cannot be linked to problems.
  `deepseek_coder/np` has no PyExamine report, so those programs have an empty `smells` value.
* Each snippet folder has 97 `solution_N.py` files for 90 answers, because the ASE split
  script cuts some answers into pieces. That is why we match through the JSON files.
* Only 183 of the 810 programs pass all their tests (Qwen 480B 62, Gemini Pro 49,
  Llama 38, DeepSeek 18, Qwen 30B 16). The paper says it analysed smells "regardless of
  whether the solution passes all functional test cases", and the `fail` flag in the JSON
  files is 0 for 539 programs that we found failing, empty or not Python. So we do not use
  that flag; we run the tests ourselves.

## Rebuild from scratch

```bash
pip install pyarrow radon
# 1. download replication_package.zip from Zenodo 10.5281/zenodo.19245562 and unzip it
# 2. download train-00000, 00001 and 00002 parquet files of deepmind/code_contests
#    at revision 802411c3010cb00d1b05bad57ca77365a3c699d6
python scripts/build_subjects.py --ase <unzipped>/replication_package/experiment1 \
    --cc train-00000-*.parquet train-00001-*.parquet train-00002-*.parquet
python scripts/verify_subjects.py
```

The build is seeded (`--seed 5570`), so the same inputs give the same 34 programs.
Both scripts use Yujie's `run_tests.py` automatically once it is in the repository
root, and fall back to `scripts/check_runner.py` (written to the Part 2 rules) until then.

## Limits

* The programs solve contest problems, not real project code. They are small (median
  34 lines) and have one input and one output, which makes behaviour easy to check
  but limits what refactoring can show.
* The models are 2025 models, not the three models we refactor with. Two of our
  refactoring models' families (Qwen, DeepSeek) also wrote some originals: 16 of
  the 34 come from Qwen or DeepSeek models. Keep `source_model` in the analysis.
* The mix is uneven: Qwen3-Coder 30B has no program left and DeepSeek has 3,
  because few of their programs pass all tests. Results per source model will be weak.
* CodeContests problems with several correct answers are removed by exact output
  comparison, so problems with one exact answer are over-represented.
* The "something to clean up" rule uses simple, common thresholds. It is a filter,
  not a measurement; Camilo's scores are the measurement.
